---
title: "Memory"
description: "Give an agent a durable filesystem it can read, write, grep, and consolidate across sessions — mounted at /mnt/memory and backed by storage you choose."
---

Memory is a durable filesystem an agent can read and write across sessions. The framework mounts it at `/mnt/memory` and routes the agent's ordinary file tools (read, write, grep, ls) there, so the model persists and recalls context with the same moves it already uses on any other directory. Nothing is mounted unless you declare it — an agent with no memory source has no memory.

Memory is a filesystem, not a query API. Search, RAG, and knowledge-graph patterns are built with eve's normal [tool system](./tools); the memory layer is for durable files the agent treats as its own scratch space and long-term notes.

A memory source is a single `memory.md` or `memory.ts` at the agent root (or an `agent/memory/` directory for multi-file setups). Both the root agent and declared [subagents](./subagents) may have one.

## Two forms

`memory.md` supplies **orientation text only** — its markdown body becomes a system pointer that tells the model how to use its memory. It declares no stores, because live storage backends cannot be expressed in markdown.

```md title="agent/memory.md"
Keep a running `index.md` at the root of each store. Append durable facts as you
learn them; never delete a user's stated preferences.
```

`memory.ts` is the full form: it declares the **stores** that get mounted, and optionally orientation text and consolidation. Use it whenever the agent needs real storage.

```ts title="agent/memory.ts"
import { defineMemory, fsStore } from "eve/memory";

export default defineMemory({
  stores: {
    notes: { backend: fsStore("./.eve/notes") },
  },
  orientation: "Persist durable facts under /mnt/memory/notes.",
});
```

## `defineMemory`

```ts
interface MemoryDefinition {
  stores: Record<string, StoreMount>; // at most 8
  orientation?: string;
  dream?: DreamConfig;
}

interface StoreMount {
  backend: MemoryStore; // the storage — and the sharing key
  path?: string; // mount sub-path under /mnt/memory; defaults to the store name
  access?: "ro" | "rw"; // defaults to "rw"
}
```

`defineMemory` is a type-level pass-through that brands the definition so the compiler and runtime can validate it. The compiler enforces the limits (at most 8 stores; markdown memory cannot declare stores).

## Stores

Each entry in `stores` mounts one backend under `/mnt/memory`. The map key is the store's **name**; by default it is also the mount path, so `notes` mounts at `/mnt/memory/notes`. Set `path` to mount elsewhere:

```ts title="agent/memory.ts"
import { defineMemory, fsStore } from "eve/memory";

export default defineMemory({
  stores: {
    notes: { backend: fsStore("./.eve/notes") }, // → /mnt/memory/notes
    "org-conventions": { backend: fsStore("./.eve/org"), path: "org", access: "ro" }, // → /mnt/memory/org (read-only)
  },
});
```

The file tools route a `/mnt/memory/...` path to the store whose mount path is the longest matching prefix. A read-only (`"ro"`) store rejects writes through the mount with an error the model sees, and does not accumulate transcripts.

### Backends

`fsStore(dir)` is the built-in backend: it persists each store as files under `dir`. Any object implementing the `MemoryStore` interface works too, so you can back a store with a database, an object store, or a network service:

```ts
interface MemoryStore {
  read(ns: MemoryNamespace, path: string): Promise<Uint8Array | null>;
  write(
    ns: MemoryNamespace,
    path: string,
    bytes: Uint8Array,
    key: string,
    options?: MemoryWriteOptions,
  ): Promise<void>;
  list(ns: MemoryNamespace, prefix: string): Promise<readonly MemoryEntry[]>;
  // grep + versioning (listVersions / readVersion) round out the contract.
}
```

The `backend` is the store's identity. The name is only a local mount alias.

## Sharing across agents

Two agents share a store by pointing at the **same backend** — regardless of what each calls it locally. Sharing is by backend identity, never by name or agent id. Give two agents the same `fsStore` directory (or the same custom backend) and they read and write the same curated memory and feed the same consolidation:

```ts title="agent/memory.ts"
import { defineMemory, fsStore } from "eve/memory";

// Agent A
export default defineMemory({
  stores: { notes: { backend: fsStore("./.eve/team") } },
});
```

```ts title="other-agent/memory.ts"
import { defineMemory, fsStore } from "eve/memory";

// Agent B — different local name, SAME backend directory → shared
export default defineMemory({
  stores: { shared: { backend: fsStore("./.eve/team") } },
});
```

Conversely, two separate backend instances never share, even under the same name.

## Consolidation (the "dream")

Every turn against a writable store dumps that session's full transcript into an off-mount area the agent cannot read — raw material, not curated memory. Consolidation (a "dream") periodically folds those transcripts into the store's curated, agent-visible memory. The curated `MEMORY.md` of each store is also injected into the agent's prompt from the first turn, so consolidated memory is always in context.

Add `dream` to turn it on. With no `run`, a built-in synthesis runs once per writable store — a single guided model call that merges new sessions into the existing memory:

```ts title="agent/memory.ts"
import { defineMemory, fsStore } from "eve/memory";

export default defineMemory({
  stores: { notes: { backend: fsStore("./.eve/notes") } },
  dream: {
    instructions: "Keep durable user preferences and project facts; drop chit-chat.",
    schedule: { idleMs: 600_000, minSessions: 3 },
  },
});
```

`schedule` controls when it fires:

- `idleMs` — re-arms a durable per-agent timer while the agent is active; it fires once the agent has been idle that long. A cron backstop sweeps any due timers.
- `cron` — a standard 5-field expression (evaluated in UTC).
- `minSessions` — a floor: don't consolidate until at least this many new sessions have accrued (counted across the agent's writable stores).

Because a store's transcripts pool every sharing agent's sessions, a shared store's dream consolidates what _all_ of them learned.

### Custom synthesis

Provide `run` to replace the pipeline wholesale — a knowledge-graph builder, a RAG indexer, anything. It receives a `DreamContext` for one store: the raw `sessions` (read-only input) and read/write access to that store's curated `memory` (the only output):

```ts title="agent/memory.ts"
import { defineMemory, fsStore, type DreamContext } from "eve/memory";

export default defineMemory({
  stores: { notes: { backend: fsStore("./.eve/notes") } },
  dream: {
    async run(ctx: DreamContext) {
      const prior = (await ctx.memory.read("index.md")) ?? "";
      const summary = await summarize(ctx.model, prior, ctx.sessions);
      await ctx.memory.write("index.md", summary);
    },
  },
});
```

The transcripts are never mutated — a dream only ever writes the curated area, so it can re-run safely.

## Versioning and concurrency

Every write that changes content records an immutable version. List and restore history through the store contract (`listVersions` / `readVersion`), and restore by reading an old version and writing it back. When agents that share a store write concurrently, the file tools use transparent compare-and-swap with bounded retry: the last writer still wins the head, but every superseded revision survives in the version trail, so nothing is silently clobbered.
